# Bake Benchmark Integration Findings

> Update, 7 November 2026: the tasks proposed below are implemented, with `benchmark:build` renamed `benchmark:prepare`. See [integration](../context/integration.md). The findings below describe the 6 November audit.

## Decision and audit scope

On 6 November 2026 the user selected two repositories: [`base-benchmark`](https://github.com/base-rs/base-benchmark) for the Bake-independent Rust implementation and `bake-benchmark` for thin Bake entry points. This supersedes the earlier single feature-gated package recommendation. Both are initial planning scaffolds, not working benchmark tooling; no migrations or new benchmark measurements were performed.

The [full audit](https://github.com/base-rs/base-benchmark/blob/main/reports/benchmarking-landscape.md) covers the **pre-creation snapshot of 19 public unarchived repositories, 64 current Rust packages, and 48 separately inventoried historical/template manifests**. It excludes the two new repositories and the unpublished local HTML prototype. Among the 12 tooling repositories (25 packages), the audit found no owned executable benchmark harness or raw measurements at the inspected revisions; the reusable contributions are task infrastructure and methodology guidance.

## Concrete findings

1. **Reuse Bake's task model.** Ordinary task attributes, namespacing, and `Registry::discover()` already register providers. Public semantic APIs should not need a Bake `Context`. A new benchmark registry is unnecessary. [Task-library boundaries](https://github.com/base-rs/bake/blob/8d4c0739694c0c305922fedc7f6ebefbfffd38fb/context/task-libraries.md#L48-L67), [registry](https://github.com/base-rs/bake/blob/8d4c0739694c0c305922fedc7f6ebefbfffd38fb/src/registry.rs#L21-L85).
2. **Discover private workloads, not release packages.** `bake_cargo::packages` intentionally returns publishable packages; using it would omit the `publish=false` workload packages preferred by Base guidance. Use explicit opt-in locked Cargo metadata, with configured standalone manifests where needed, never recursive historical snapshot discovery. [Public API](https://github.com/base-rs/bake-cargo/blob/8687e0392a7425bf2b6dfe2f5fb6f38ae58f12fc/src/lib.rs#L45-L49), [filtering](https://github.com/base-rs/bake-cargo/blob/8687e0392a7425bf2b6dfe2f5fb6f38ae58f12fc/src/cargo.rs#L77-L123), [benchmark guidance](https://github.com/base-rs/base-project/blob/5de408e4cd77a2ff9eb21a9039d27c2094f8939e/context/benchmarks.md#L13-L25).
3. **Keep preparation outside collection.** Freeze source, toolchain, features, lockfile, build flags/command, and executable identity before measurement. Shared core supervision must own cancellation/cleanup and the experiment lock across all server/client roles. Bake should translate plans, not own another loop. [Scheduler writes](https://github.com/base-rs/base-scheduler/blob/cd51eeeee29c0658722868355b1bc04f7e2679ec/benchmarks/writes/run.py#L56-L184), [HTTP readiness/final statistics](https://github.com/base-rs/base-http/blob/90d6b1f6cc0e99094b2f3c5d5548b3e7366e64b5/benchmarks/client/run.py#L28-L87).
4. **Registration and guidance discovery are different.** Regeneration links ordinary direct task dependencies; installed `context/**` explains usage but is not a workload execution inventory. Bake's own JSON output is not a raw sample journal. [Dependency linking](https://github.com/base-rs/bake/blob/8d4c0739694c0c305922fedc7f6ebefbfffd38fb/src/bin/cargo-bake/project.rs#L384-L408), [context installer](https://github.com/base-rs/bake-agent-context/blob/591b5af4162f397cbdd5356b0ff596d86cbccd42/context/usage.md#L25-L81).
5. **CI is correctness evidence, not a controlled benchmark host.** Scheduler includes workload members, while HTTP excludes benchmark suites from its main workspace. Explicit scope matters, and `bake-test` makes all-targets opt-in. [Scheduler workspace](https://github.com/base-rs/base-scheduler/blob/cd51eeeee29c0658722868355b1bc04f7e2679ec/Cargo.toml#L1-L49), [HTTP workspace](https://github.com/base-rs/base-http/blob/90d6b1f6cc0e99094b2f3c5d5548b3e7366e64b5/Cargo.toml#L1-L36), [test task](https://github.com/base-rs/bake-test/blob/72de25667bad4b1ce048fe6d9446ec55ef5e3909/src/lib.rs#L29-L86).

## Proposed implementation

The later [scheduler consumer review response](https://github.com/base-rs/base-benchmark/blob/main/reports/external-review-response.md) extends preparation to labelled source trees/archives, downstream patch overrides, and baseline-copy rebuild controls. Run plans should preserve randomized same-round comparators, explicit screening/recorded modes, declared load-error outcomes distinct from correctness failures, measurement-host placement/locking, and progress while waiting. These belong in shared core APIs, not a new Bake-only comparison runner. The review's quantitative observations were not independently verified in this audit.

Provide `benchmark:list`, `benchmark:build`, `benchmark:smoke`, `benchmark:run`, and `benchmark:summarize`, all delegating semantic operations to core Rust APIs. These names are proposals; **none is registered in this scaffold**. See the [integration plan](../context/integration.md).

No Python orchestration dependency, duplicate runner/statistics implementation, or universal workload trait should be introduced. Preserve historical scripts/results as evidence; port reusable behavior and regression cases instead of wrapping them. Exact task arguments, manifest schema, API/version compatibility, and feature choices remain open. Hardware-counter phase matching remains unimplemented and must not be hidden by dividing whole-process totals by loop counts.
